# SWE-smith

A self-contained, implementation-focused tutorial for SWE-smith, using
[`tutorials/_shared/docker_exec.py`](../_shared/docker_exec.py) (generic Docker-run/sentinel
-parsing plumbing shared across the three Docker-based tutorials in this directory).

Companion script: [quickstart.py](quickstart.py).

```bash
pip install datasets
# needs a running Docker daemon
python tutorials/swe-smith/quickstart.py --n-tasks 2 --structural-only   # no daemon needed, prints the scripts
python tutorials/swe-smith/quickstart.py --n-tasks 2                       # real run — pulls a multi-GB image per task
```

## 1. Dataset overview

SWE-smith is a **bug-injection** benchmark: real open-source repos with a synthetic bug
mechanically injected into a real commit, paired with a prebuilt Docker image already set up with
that repo's dependencies. Unlike BigCodeBench/DS-1000, grading needs a full repo checkout and test
suite — there's no self-contained inline test.

- **Source**: [`SWE-bench/SWE-smith`](https://huggingface.co/datasets/SWE-bench/SWE-smith) on the
  Hugging Face Hub. **Split: `train`.**
- This tutorial loads a shuffled (seed 42), capped pool rather than the full ~59K rows — scanning
  all of them just to sample a handful costs real minutes on every run.

### Schema (fields this tutorial's code touches)

| Field | Meaning |
|---|---|
| `instance_id` | Dataset-native task id, e.g. `pydicom__pydicom.7d361b3d.func_pm_class_rm_funcs__jufdn9ut`. |
| `problem_statement` | Natural-language bug description. A meaningful fraction of rows are synthetic mutation tasks with NO generated description — this tutorial filters those out, same as the real pipeline. |
| `patch` | **The gold FIX** — but applied to a CLEAN image, this patch's presence is what creates the bug in the first place (see below). |
| `image_name` | A prebuilt, per-instance Docker image already tagged on the row — no build step needed, `docker run` pulls it implicitly on first use. |
| `FAIL_TO_PASS`, `PASS_TO_PASS` | Lists of pytest node ids: tests that must go from failing to passing (or must keep passing) once the bug is genuinely fixed. |

**The single most important thing to internalize about this dataset**: the image starts in a
CLEAN state, not a buggy one. `patch` is the diff that, applied FORWARD, introduces the bug —
because SWE-smith bugs are synthetically generated by taking a real historical bug-fix commit and
inverting it. Every grading mode therefore starts with the same setup step: apply `patch` forward
to establish the buggy baseline, before doing anything else.

## 2. Implementation

### Loading

```python
from datasets import load_dataset

ds = load_dataset("SWE-bench/SWE-smith", split="train").shuffle(seed=42)
tasks = []
for row in ds:
    if len(tasks) >= 500:  # pool cap — see section 1
        break
    if row.get("problem_statement") and str(row["problem_statement"]).strip():
        tasks.append(dict(row))
```

### Grading, step by step

All grading happens inside the row's own `image_name` container, via one `docker run -i` call per
grading attempt with the whole shell script piped over stdin (see
[`_shared/docker_exec.py`](../_shared/docker_exec.py) for why: a container's exit code is never
trusted, and a large script/patch is never passed as an argv string).

1. **Setup (every mode)**: `cd /testbed`, write `row["patch"]` to `/tmp/bug.patch`, `git apply` it.
   This establishes the buggy baseline described in section 1. A failed apply here is OUR harness's
   fault (`error_harness`), not the candidate's — nothing about the model's own solution has been
   touched yet.
2. **Grading a real candidate solution** (`grade()`): if the solution is an empty string, return
   `fail` directly without touching Docker at all — an empty patch trivially leaves the bug
   unfixed. Otherwise, after setup, write the candidate's patch to `/tmp/candidate.patch` and `git
   apply` it. **This apply failing IS a real candidate failure** (`fail`, not `error_harness`) —
   unlike the bug-patch apply in setup, a model producing an unparseable diff is the model's own
   failure to solve the task correctly.
3. **Reference control** (`grade_reference()`): after the same setup, `git apply -R /tmp/bug.patch`
   — reversing the SAME patch that created the bug, a round trip back to the clean, correct state.
   Must score ~100% pass; a reverse-apply failure here is `error_harness` (our own setup/checkout
   problem), never blamed on "the candidate."
4. **Null control** (`grade_null()`): setup only, no fix applied — must score ~0% pass.
5. **Running tests**: after
   `source /opt/miniconda3/etc/profile.d/conda.sh && conda activate testbed`, run `cd /testbed &&
   python -m pytest -q <FAIL_TO_PASS node ids> <PASS_TO_PASS node ids>` (shell-quoted, space-joined
   — passed directly as pytest node-id arguments, not by parsing a full-suite log). The script's
   last action checks pytest's own exit code (`$?`) and echoes the sentinel PASS/FAIL line
   accordingly.

```python
# see quickstart.py for the full, runnable version
def grade(row: dict, solution: str, timeout_seconds: int = 600) -> docker_exec.GradeResult:
    if not solution.strip():
        return docker_exec.GradeResult(outcome="fail", detail="empty patch — bug remains unfixed")
    # setup (apply bug patch) + apply candidate patch + run pytest, all inside one docker_exec.run()
    ...
```

**Pitfall — conda activation path**: this dataset's images activate via
`source /opt/miniconda3/etc/profile.d/conda.sh && conda activate testbed`. The SWE-Gym tutorial
uses a *different* path (`source /opt/miniconda3/bin/activate && conda activate testbed`) — don't
assume the two datasets' images are interchangeable just because both use conda + a `testbed` env
name; this was confirmed directly against real images, not assumed identical.

## 3. Evaluation

### Custom harness

Run the reference and null controls — the same grader-validation pattern used throughout this
tutorial series:

```python
row = tasks[0]
print(grade_reference(row))   # expect outcome == "pass"
print(grade_null(row))        # expect outcome != "pass"
```

If reference doesn't score ~100% or null doesn't score ~0% across a real sample, the grader is
broken — stop and fix it before trusting anything it reports about a real model.

### Official harness cross-check

SWE-smith's images and conventions descend from **SWE-bench's own evaluation harness**
([`princeton-nlp/SWE-bench`](https://github.com/princeton-nlp/SWE-bench) on GitHub, `pip install
swebench`). A known, deliberate divergence worth cross-checking: this tutorial's harness (and this
repo's own) passes `FAIL_TO_PASS`/`PASS_TO_PASS` node ids **directly as pytest arguments**, rather
than SWE-bench's own whole-file-plus-log-parsing approach. This trades away per-test granularity
within a single run in exchange for a much simpler, uniform sentinel-based result protocol shared
across all three Docker-based tutorials here.

To cross-check: run the official `swebench` harness against the same (instance, patch) pairs and
confirm its FAIL_TO_PASS/PASS_TO_PASS verdicts agree with this tutorial's PASS/FAIL outcome. As
with the other tutorials in this series, **verify exact current CLI flags against `swebench`'s own
`--help`/README** rather than trusting any specific invocation asserted here — this tutorial can't
run that external tool from where it's written to confirm currentness.
